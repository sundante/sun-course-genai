# Concept Review - Agent Engineering

Short-form review for [17 - Agent Engineering](../17-Agent-Engineering/INDEX.mdx). The full question bank is the module's [Q&A Review Bank](../17-Agent-Engineering/Notes/09-Interview-QA-Bank.mdx).

## Harness, Loop & Graph Questions

**Q: What is the "Agent = Model + Harness" framing, and why does it matter?**
The model supplies the intelligence; the harness - loop and bounds, tools and execution environment, state, context management, verification and conventions like `AGENTS.md` - makes it useful. Two teams on the same model can get very different results because of harness differences, which is why OpenAI and Anthropic both describe engineers' work shifting towards designing the environment agents work in.

**Q: How do long-running agents make progress across many context windows?**
By keeping state outside the conversation: an initializer session creates a feature list with statuses, a startup/test script, a progress log and a first commit; each later session reads them, runs smoke tests, completes and verifies one feature, commits and updates the log (Anthropic, *Effective harnesses for long-running agents*, 2025).

**Q: Why shouldn't a generator agent grade its own output?**
Models tend to rate their own work generously and declare success early. A separate evaluator with explicit, agreed criteria - or tests the harness runs itself, such as a stop hook - catches what self-review misses. Self-critique without external feedback often fails to improve answers (Huang et al., 2023).

**Q: When should a loop become a graph?**
When you can name the reason: distinct specialities, parallel sub-tasks, different models or tools per step, auditable branching with approvals, or a verifier large enough to be its own step. The sharpest test is failure semantics - if an interrupted run must resume rather than restart, use a checkpointed graph or durable execution.

## Context Questions

**Q: What is context rot, and why is a bigger context window not a fix?**
Model performance degrades as input grows and fills with irrelevant or stale content, well within advertised limits (Chroma's 2025 study of 18 models; lost-in-the-middle effects). A bigger window raises capacity, not attention quality; the fix is curation - just-in-time retrieval, clearing old tool results, compaction, offloading, notes and sub-agents.

**Q: How do coding agents load a repository into context?**
Mostly just in time: they read `AGENTS.md`/`CLAUDE.md` at the start, then explore with search and file reads, rather than putting the codebase into the prompt.

## Coding & Computer-Use Agent Questions

**Q: What makes a repository agent-ready?**
A short `AGENTS.md` with build, test and lint commands and non-obvious conventions; fast deterministic checks; clear task specs; architecture enforced by lint rules and tests; an isolated environment without production secrets.

**Q: What did METR's 2025 randomised trial find about AI coding tools?**
Experienced open-source developers in their own mature repositories took 19% longer with early-2025 AI tools, although they expected - and afterwards believed in - a speed-up. Measure outcomes, not impressions.

**Q: When would you use pixel-based computer use instead of an API?**
Only when there is no API or structured (DOM/accessibility-tree) access - for example legacy desktop software. It is slower, costlier and less reliable, and browser agents with logged-in sessions face the full lethal trifecta.

## Skills, Verifiers & Delivery Questions

**Q: What is a skill, and how does progressive disclosure work?**
A directory with a `SKILL.md` (frontmatter `name` and `description`, then instructions) plus optional scripts, references and assets - an open standard. Only names and descriptions load at start; the body loads when the skill is used; referenced files and scripts load only when needed.

**Q: Why prefer deterministic checks over LLM-as-judge where possible?**
Outcome checks and executable tests avoid the judge's biases (position, length, self-preference) and are much harder to game. Where a judge is needed, use per-criterion rubrics validated against human labels.

**Q: What is reward hacking in agents, and how do you defend against it?**
Satisfying the verifier without doing the task - editing tests, special-casing visible examples, reading answers, claiming success. METR documented frontier models doing this in 2025. Defences: hidden tests, verifiers isolated from the agent's sandbox, state-based outcome checks.

**Q: What is the difference between "vibe coding" and "vibe engineering"?**
Vibe coding (Karpathy, 2025) accepts AI-written code if it runs - fine for prototypes. Vibe engineering (Willison, 2025) uses coding agents on production software with tests, plans, documentation, version control and review.

**Q: In spec-driven development, what do humans review?**
The spec and plan (the cheapest point to fix building the wrong thing), the tests that enforce the acceptance criteria, and high-risk outcomes - rather than every line of routine generated code. Spec and tests change together.
